## 宿題

- 取り組んだレベル：基礎
- やったこと：
  - `app/tools.py` の `search_glossary` の docstring を1行だけ変えた
    - 変更前：「query には調べたい用語を1つだけ入れる（例: "LoRA"）」
    - 変更後：「query には調べたい用語をまとめて入れる（例: "LoRA QLoRA"）」
  - 変更の前と後で、同じ質問「LoRAとQLoRAの違いは？」を `--trace` 付きで3回ずつ実行して比べた
  - `--list-tools` で、モデルに見える説明文が変わったことを確認した
- 結果：
  - 変更前：3回とも `search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` を2回に分けて検索。requests=2、tool_calls=2、入力トークンは1416
  - 変更後：3回とも `search_glossary({'query': 'LoRA QLoRA'})` の1回にまとめて検索。requests=2、tool_calls=1、入力トークンは1111
    - trace の tool return は途中で切れていたので、`tools.search_glossary('LoRA QLoRA')` を直接実行して確かめたところ、LoRA と QLoRA の両方が返っていた
  - 回答は変更前・変更後とも用語集の定義どおりで正しかった。言い回しや長さ（出力トークン174〜224）は毎回変わった
- 気づき・疑問：
  - docstring の1行（指示の「1つだけ入れる」⇒「まとめて入れる」、と、例の `"LoRA"` ⇒ `"LoRA QLoRA"`）を変えるだけで、モデルが決める引数と呼び出し回数がはっきり変わった。docstring はモデルへの指示として働いている。ただし今回は指示の言葉と例を同時に変えたので、どちらが効いたのかはわからない。例だけを `"LoRA QLoRA"` にして言葉は「1つだけ入れる」のままにする、など1か所ずつ変えて試せば区別できそう
  - まとめて検索しても正しく答えられたのは、検索がスペースを除いて部分一致で探す作りだったから。完全一致で探す作りなら、まとめた検索は見つからず、回答の質が下がったかもしれない。ツールの説明文は、ツールの実装に合わせて書く必要がある
  - requests はどちらも2回で変わらなかった。モデルは2つの検索も1回の応答でまとめて頼んでいたので、ツールの呼び出し回数が減っても LLM の呼び出し回数は減らない
  - 入力トークンが約300減った。変更前は「LoRA」の検索でも QLoRA が部分一致で返るなど、重なる結果が2つ分モデルに渡っていたためだと考えられる
  - 演習で `make_quiz` を追加したあと、同じ質問の入力トークンが1196から1416に増えていた。使わないツールでも、説明文の分だけ毎回の入力が増える
  - 検索を分けるのとまとめるのでは、どちらがよい設計なのか。用語が多いと、まとめた検索は上限の3件を超えて取りこぼしそうである
